# qtsctl — внешнее управление KR QTS

Как пользоваться запуском, запаковкой и диагностикой QTS из командной строки,
из задачи редактора или из своего инструмента.

Это руководство пользователя. Почему оно устроено именно так и что будет
дальше — в [CLI.md](CLI.md).

---

## 1. Чем запускать

Два способа, оба равноценны:

```
F:\KR_ServerManager\dist\KR_QTS\qtsctl.exe   собранный
python F:\KR_ServerManager\qtsctl.py         из исходников
```

Справка работает всегда — даже если программа не запущена и не настроена:

```
qtsctl -help              общая страница с примерами
qtsctl -help commands     что делает каждая команда
qtsctl -help mods         подключение модов и сорсов
qtsctl -help pack         запаковка
qtsctl -help params       полный список параметров клиента и сервера
qtsctl -help output       ожидание и вывод
qtsctl -help exit         коды возврата
qtsctl -help -json        то же самое машине
```

---

## 2. Как это устроено в целом

**Пресет — база, аргументы — накладка на один запуск.** Пресет настроен один
раз в окне и содержит всё: пути, режим, порт, моды, параметры. Командная
строка уточняет конкретный прогон и **в пресет не пишется** — следующий запуск
снова чистый.

Единственное, что запоминается навсегда, — привязки модов и сорсов (раздел 5).
Это сделано намеренно: указав их один раз, длинную команду больше не пишешь.

**Правило знаков одно на всю грамматику:**

> **`-` — «ровно это»**: задать значение, заменить список, выключить флаг.
> **`+` — «сверх того, что есть»**: добавить к списку, включить флаг.

Разделитель списков — запятая. Регистр не важен: `+cfilepatching` и
`+cFilePatching` — одно и то же.

## 3. Команды

| Команда | Что делает |
|---|---|
| `qtsctl -preset dev +server` | запуск (глагол можно не писать) |
| `qtsctl restart +server` | потушить и поднять снова; если ничего не работало — просто поднять |
| `qtsctl stop` | потушить всё, что работает |
| `qtsctl stop +server` | потушить только сервер |
| `qtsctl stop +hard` | не дожидаясь корректного завершения |
| `qtsctl status` | что сейчас работает |
| `qtsctl show` | показать окно программы |
| `qtsctl quit` | завершить программу (**сервер продолжит работать**) |

`-preset` можно не писать: возьмётся тот, что выбран в окне. Пресет ищется и по
отображаемому имени, и по имени файла, регистр не важен.

**Если QTS не запущен**, команда вернёт код 7 и подскажет. Чтобы поднять его
молча, без окна, — `+start`:

```
qtsctl -preset dev +server +start
```

Программа появится значком в трее и выполнит команду. Вручную то же самое:
`KR_QTS.exe --quiet`.

## 4. Что происходит при запуске

Порядок фиксированный, и от него зависят условия ниже:

1. **Убиваются старые процессы** — только тех видов, что сейчас запускаем.
   Перезапуск клиента не роняет живой сервер.
2. **Запаковка** изменённых модов, если включена.
3. **Junction-ссылки** на все моды запуска в служебную папку рядом с игрой.
   Поэтому папка мода может лежать где угодно, хоть на другом диске.
4. **Копирование `.bikey`** в `keys` сервера — только в режиме dedicated.
5. **Сервер**, ожидание реальной готовности, а не отсчёт секунд.
6. **Клиент**.

## 5. Моды — все случаи

### 5.1. Мод уже подключён к пресету

**Ничего писать не надо.** Он запустится, а если у него привязаны сорсы и они
изменились — пересоберётся при `+pack`.

### 5.2. Мод есть в списке модов приложения, но не в пресете

```
qtsctl -preset dev +server +mod=@KR_Test
```

Добавится **в конец** списка загрузки на этот запуск. В конец, а не в
середину: порядок в списке есть порядок загрузки, и вставлять чужое посередине
значит менять поведение молча.

Только на сервер:

```
qtsctl -preset dev +server +serverMod=@KR_Admin
```

Заменить весь список целиком — запустить ровно с этими:

```
qtsctl -preset dev +server -mod=@KR_Core,@KR_Test
```

### 5.3. Мод в списке, но сорсы к нему не привязаны

Программа знает, **куда** паковать (папка мода), но не знает, **что**.
Привязываем:

```
qtsctl -preset dev +server +mod=@KR_Test +src=P:\KR\Test_Scripts
```

Папок сорсов может быть несколько — каждая даёт свой PBO:

```
+mod=@KR_Test +src=P:\KR\Test_Scripts +src=P:\KR\Test_GUI
```

**Привязка запоминается навсегда.** Со следующего раза достаточно
`+mod=@KR_Test`, а если мод в пресете — вообще ничего.

### 5.4. Мода нет нигде

Программа не знает ни что паковать, ни куда. Даём и то и другое — папку мода и
папку сорсов:

```
qtsctl -preset dev +server +mod=F:\Builds\@KR_New +src=P:\KR\NewFeature
```

Что произойдёт: мод заведётся в реестре под именем папки (`KR_New`), его папка
добавится в «свои моды» в настройках (чтобы он пережил следующее
сканирование), сорсы привяжутся, мод подключится к запуску. Всё это будет
названо в отчёте.

**Со второго раза это обычный мод из списка** — то есть случай 5.1 или 5.2.

### 5.5. Правило принадлежности сорсов

**`+src=` относится к последнему `+mod=` перед ним.** Читается слева направо:

```
qtsctl -preset dev +server +client ^
  +mod=@KR_Core ^
  +mod=@KR_Test              +src=P:\KR\Test_Scripts +src=P:\KR\Test_GUI ^
  +mod=F:\Builds\@KR_New     +src=P:\KR\NewFeature ^
  +serverMod=F:\Builds\@KR_Admin +src=P:\KR\Admin ^
  +pack
```

Четыре мода в трёх разных состояниях — и никакой неоднозначности.

Если команду собирает **программа** и порядок аргументов может перепутаться при
правке кода, есть явная форма, где мод назван прямо:

```
+src:@KR_Test=P:\KR\Test_Scripts
```

### 5.6. Отвязать и забыть

```
+mod=@KR_Test -src=P:\KR\Test_GUI     снять привязку одной папки
-forget=@KR_New                       забыть запись о моде целиком
```

**`-forget` не трогает файлы никогда** — ни папку мода, ни сорсы. Это только
про записи в приложении.

### 5.7. Что сообщается сразу

* `+src=` раньше первого `+mod=` — отказ, а не «применю к чему-нибудь».
* Одна папка сорсов у двух модов — не запрещено, но названо в отчёте: почти
  наверняка это ошибка.
* Повторная привязка той же папки ничего не делает: команду можно звать хоть
  каждый раз.

## 6. Запаковка

```
+pack             паковать, как настроено в программе
+pack=normal      быстрая сборка (-C)
+pack=full        полная, с бинаризацией (+C)
-pack             не паковать вовсе
+rebuild          собрать всё, а не только изменившееся
```

Условия, которые важно знать:

1. **Пакуются моды этого запуска** — из пресета плюс добавленные через
   `+mod=`. Не «моды пресета».
2. **Пакуются только свои локальные моды с привязанными сорсами.** Моды из
   Steam и скачанные с GitHub не пакуются никогда: они приходят собранными.
3. **Пакуется изменившееся** — сравниваются даты файлов сорсов и готового PBO.
   `+rebuild` нужен, когда изменилось не содержимое, а условия сборки:
   настройки pboProject, версия инструментов.
4. **Если DayZ уже работает, запаковка пропускается** с предупреждением:
   запущенная игра держит PBO открытыми. Запуск идёт со старыми PBO — и об этом
   сказано, а не замолчано.
5. **pboProject на машине один.** Если параллельно пакует что-то ещё, встаём в
   очередь.
6. **На первой неудаче запуск отменяется**, наружу уходит код 3 и причина.

Отчёт по каждому PBO:

```
Запаковка (3):
  KR_Core_Scripts.pbo  ок       34.2 c
  KR_Core_GUI.pbo      ок        3.1 c   предупреждений 2
  KR_Test.pbo          ошибка    0.9 c   ошибок 4

Ошибка запаковки KR_Test. Запуск отменён.
```

## 7. Параметры клиента и сервера

Приставка `c` — клиенту, `s` — серверу, для тех параметров, что есть у обоих:

```
+cFilePatching -sFilePatching     включить у клиента, выключить у сервера
+cNoPause +sNoPause
-sCpuCount=4 -sLimitFPS=60
```

Параметры, которые бывают только у одной стороны, идут **без приставки** —
путать нечего:

```
-storage=D:\st       только сервер
-window              только клиент
-name=Тест           только клиент
```

Пустое значение **снимает** параметр, заданный в пресете:

```
-cScrDef=            не передавать его вовсе
```

Это не то же самое, что выключить: `-cFilePatching` передаст
`-filePatching=0`, а `-cScrDef=` не передаст ничего.

Чего мы не знаем — передаётся насквозь:

```
-cExtra="-world=empty -noSplash"
-sExtra="-someNewFlag"
```

Полный список: `qtsctl -help params`.

## 8. Ожидание и результат

**Ожидание включено по умолчанию** для `launch`, `restart` и `stop`: команда
стоит, пока запрошенное не поднимется или не погаснет, и печатает окончательный
отчёт. Потолок — 300 секунд, меняется `-wait=180`. Вернуться сразу — `+detach`.

Время запаковки считается **отдельно** от ожидания: долгая сборка не съедает
время, отведённое на подъём сервера.

Коды возврата отвечают только на вопрос «поднялось или нет»:

| Код | Значение |
|---|---|
| 0 | всё запрошенное поднялось |
| 1 | не понял аргументы |
| 2 | нет пресета, программа не настроена или занята |
| 3 | запаковка не удалась |
| 4 | сервер не поднялся за отведённое время |
| 5 | клиент не поднялся |
| 6 | упало уже после старта |
| 7 | не удалось связаться с QTS |

**Ошибки скриптов на код возврата не влияют никогда.** Они идут в отчёте
отдельным списком: сообщить факт — наше дело, решать, что с ним делать, —
твоё.

«Поднялся» означает: скрипты собрались (слой `5_Mission` компилируется
последним). Для клиента это **не** значит «вошёл на сервер» — он может стоять
в меню.

**Отчёт отдаётся всегда, в том числе при провале** — там он нужнее всего. В
нём: стороны порознь, PID, порт, время, счётчик ошибок скриптов, что заведено
и привязано из модов и **прямые пути ко всем логам** — RPT, `script.log`,
консоль сервера, крэш-дампы. Искать их не надо.

Машинный вид — `-json`, разбирается любым языком.

## 9. Настройки

В окне, раздел **«Внешнее управление»**: выключатель, готовая команда для этой
машины и те же примеры с кнопкой «скопировать». Если выключить — движок ответит
«внешнее управление выключено» и скажет, где включить, а не промолчит.

## 10. Чего оно не делает — знать заранее

1. **Зависимости модов не подтягиваются.** В окне при подключении мода
   приложение предупреждает о его зависимостях; через командную строку этого
   нет. Пишешь `+mod=X` — получаешь ровно X. Зависимости перечисляй сам.
2. **У свежесобранного мода может не быть `.bikey`.** Если сервер проверяет
   подписи, клиент не войдёт. В отчёте это названо, но само не чинится.
3. **Накладка не видна в окне.** В журнал пишется строка «— Запуск извне:
   пресет «...» —», но галки и поля показывают пресет, а не то, с чем реально
   запущено.
4. **Один запуск за раз.** Пока идёт подготовка или остановка — код 2 и
   «программа занята».
5. **Только эта машина.** Достучаться до QTS с другого компьютера нельзя и не
   будет можно: это инструмент локальной отладки.
6. **`quit` не гасит сервер.** Он отдельный процесс и переживает закрытие
   менеджера — это сделано намеренно.

## 11. Готовые рецепты

**Задача в VS Code** — собрать и поднять сервер:

```json
{ "label": "DayZ: сервер",
  "type": "shell",
  "command": "F:\\KR_ServerManager\\dist\\KR_QTS\\qtsctl.exe",
  "args": ["-preset", "dev", "+server", "+pack", "+start"],
  "problemMatcher": [] }
```

**Цикл отладки мода** — пересобрать и перезапустить только сервер:

```
qtsctl restart +server +pack
```

**Проверить новый мод, которого ещё нет в приложении:**

```
qtsctl -preset dev +server +mod=F:\Builds\@KR_New +src=P:\KR\NewFeature +pack
```

**Собрать и ничего не запускать:**

```
qtsctl -preset dev -server -client +pack
```

**Посмотреть, что сейчас происходит:**

```
qtsctl status
qtsctl status -json    для скрипта
```
