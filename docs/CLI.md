# Внешнее управление KR QTS

Рабочий документ. Описывает, как сторонние инструменты пользуются запуском,
запаковкой и диагностикой QTS, не повторяя их у себя.

Собран из обсуждения и сверен с кодом: всё, на что здесь есть ссылка, уже
существует и работает.

---

## 1. Зачем

QTS сделан для отладки модификаций, и для обычного пользователя окна достаточно.
Но два сценария окном не закрываются.

**Запуск из редактора.** Не открывать приложение и не жать кнопки, а держать
задачу в VS Code: собрал — поднял сервер — посмотрел лог.

**Автономная работа помощника.** Мы пишем мод вдвоём, и сейчас цикл такой:
человек собирает, запускает, смотрит, пересказывает результат. Если ту же
последовательность может выполнить инструмент, цикл замыкается без пересказа —
это и есть основная экономия.

Отсюда главное требование, из которого следует всё остальное: **запустить —
десять процентов дела, девяносто — узнать результат.**

---

## 2. Модель

**Пресет — база, аргументы — накладка на один запуск.**

Пресет настроен один раз и содержит всё необходимое. Аргументы командной строки
уточняют конкретный прогон и **никогда не записываются в пресет**: следующий
запуск снова чистый.

Единственное исключение — привязки модов и сорсов (раздел 5): они по своей
природе постоянные и запоминаются намеренно.

Из накладки следует требование к окну: **если запуск идёт с накладкой, окно
обязано это показывать.** Иначе человек смотрит в пресет, видит выключенный
`filePatching`, а он работает, — и полчаса ищет мистику.

---

## 3. Правило плюса и минуса

Одно правило на всю грамматику. Если оно понято, остальное выводится:

> **`-` — «ровно это»**: задать значение, заменить список, выключить флаг.
> **`+` — «сверх того, что есть»**: добавить к списку, включить флаг.

```
-preset dev          задать пресет
-mod=A,B             заменить список модов целиком
+mod=C               добавить к тому, что в пресете
-cFilePatching       выключить у клиента, даже если в пресете включён
+cFilePatching       включить у клиента, даже если в пресете выключен
```

Разделитель списков — **запятая**. Точка с запятой принимается как синоним, но
не показывается нигде: в PowerShell она разрывает команду, и сценарий
«скопировал из документации — не работает» недопустим.

Регистр не важен: `+cfilepatching` и `+cFilePatching` — одно и то же.

## 4. Грамматика

### Основное

| Аргумент | Что делает |
|---|---|
| `-preset <имя>` | база запуска |
| `+server` `+client` | что поднимать |
| `-server` `-client` | наоборот, не поднимать, даже если в пресете отмечено |
| `+start` | поднять QTS, если он не запущен: без окна, в трей |
| `-wait[=сек]` | ждать готовности |
| `-timeout=сек` | потолок ожидания |
| `+detach` | вернуться сразу, не дожидаясь |
| `-json` | машинный отчёт вместо человеческого |
| `-help [раздел]` | справка (раздел 8) |

### Параметры сторон

Строятся **из справочника** [core/params.py](../core/params.py), а не пишутся
руками. Каждый `ParamSpec` знает свою сторону (`SERVER` / `CLIENT` / `BOTH`),
тип и описание на трёх языках. Отсюда:

* параметр с `target=BOTH` даёт две формы — `+cFilePatching` и `+sFilePatching`;
* односторонний идёт без префикса: `-storage=` только серверный, `-window`
  только клиентский, путать нечего;
* тип решает форму: `FLAG` → `+имя` / `-имя`, `INT` и `STR` → `-имя=значение`,
  `SWITCH` → `+имя` / `-имя` (разворачивается в `-имя=1` / `-имя=0`).

**Добавили параметр в справочник — он сам появился в командной строке, в справке
и в форме настроек.** Расходиться нечему.

| Пример | Значение |
|---|---|
| `+cFilePatching` `-sFilePatching` | флаг стороне поверх пресета |
| `-sCpuCount=4` `-cLimitFPS=60` | значение стороне |
| `-cExtra="-world=empty"` | сквозной проход того, чего мы не знаем |

`-cExtra` и `-sExtra` ложатся на существующие поля пресета `extra_client` и
`extra_server`. Они нужны, чтобы новый параметр Bohemia не требовал выпуска
новой версии QTS.

### Моды

| Аргумент | Что делает |
|---|---|
| `-mod=A,B` | заменить список целиком, порядок = порядок загрузки |
| `+mod=C` | добавить к тому, что в пресете, **в конец** |
| `+serverMod=D` | то же, но только на сервер |
| `+src=<папка>` | привязать папку сорсов к последнему `+mod=` |
| `-src=<папка>` | снять привязку |
| `+src:@Имя=<папка>` | явная форма: мод назван, порядок не важен |
| `-forget=@Имя` | забыть запись о моде |

Сторона выражается ключом, а не отдельным флагом: `+mod=` — клиент и сервер,
`+serverMod=` — только сервер.

### Запаковка

| Аргумент | Что делает |
|---|---|
| `-pack` | не паковать вообще |
| `+pack` | паковать как настроено в приложении |
| `+pack=normal` | быстрая сборка (`-C`) |
| `+pack=full` | полная, с бинаризацией (`+C`) |
| `+rebuild` | пересобрать всё, не только изменённое |

Тип сборки и её объём — **разные оси**, и смешивать их в одном аргументе нельзя:
`+pack=full +rebuild` читается, `+pack=full-rebuild` — уже нет.

### Управление

| Команда | Что делает |
|---|---|
| `qtsctl stop [+server] [+client]` | потушить |
| `qtsctl status [-json]` | что сейчас работает |
| `qtsctl show` | показать окно |
| `qtsctl quit` | завершить движок |

## 5. Моды и сорсы

### Три случая

Различаются тем, что программа знает:

| Случай | Знает | Форма |
|---|---|---|
| Мод в списке, сорсы привязаны | всё | `+mod=@KR_Test` |
| Мод в списке, сорсов нет | куда паковать | `+mod=@KR_Test +src=P:\KR\Test_Scripts` |
| Мода нет нигде | ничего | `+mod=F:\Builds\@KR_New +src=P:\KR\NewFeature` |

Второй и третий случай — **не параметры запуска, а регистрация.** Указав их один
раз, ты превращаешь случай в первый навсегда: дальше это обычный мод из реестра,
и команда снова короткая. Запоминаем по умолчанию; `-forget=@Имя` убирает запись.

**`-forget` не трогает файлы никогда** — ни папку мода, ни сорсы. «Забыть» — это
только про наши записи. Удаление чужих файлов из скрипта однажды сотрёт чью-то
работу.

### Правило принадлежности

**`+src=` относится к последнему `+mod=` перед ним.** Читается слева направо,
экзотических разделителей не требует (`>` съест перенаправление вывода, `;`
разорвёт команду в PowerShell), и само решает случай нескольких папок сорсов у
одного мода — а он обычный: `@KR_Core` это и `Core_Scripts`, и `Core_GUI`.

```
qtsctl -preset dev +server +client ^
  +mod=@KR_Core ^
  +mod=@KR_Test              +src=P:\KR\Test_Scripts +src=P:\KR\Test_GUI ^
  +mod=F:\Builds\@KR_New     +src=P:\KR\NewFeature ^
  +serverMod=F:\Builds\@KR_Admin +src=P:\KR\Admin ^
  +pack -wait
```

Четыре мода в трёх разных состояниях, у одного две папки сорсов, один
серверный — и никакой неоднозначности.

Для команд, которые собирает **программа**, есть вторая форма — `+src:@KR_Test=P:\KR\Test_Scripts`.
Тот же смысл, но мод назван явно и порядок аргументов не важен: при рефакторинге
генератора позиционная запись ломается тихо, а это недопустимо.

### Что обязано соблюдаться

1. **`+src=` до первого `+mod=` — ошибка**, а не «применю к чему-нибудь».
2. **`+src=` добавляет, `-src=` снимает.** Повторная привязка той же папки
   ничего не ломает: команду можно звать хоть каждый раз.
3. **Одна папка сорсов у двух модов** — не запрещаем, но сообщаем: PBO
   собирается по имени папки, и почти наверняка это ошибка.
4. **Зависимости подтягиваются** так же, как в приложении, и **пишутся в
   отчёт**. Иначе `+mod=X` из скрипта и `+mod=X` мышкой дают разный запуск.
5. **Порядок:** добавленные через `+mod=` встают в конец; `-mod=` задаёт весь
   порядок целиком.

### Ключи — засада третьего случая

При запуске `.bikey` мода копируется в `keys` сервера
([core/mods.py:586](../core/mods.py#L586)). У свежесобранного мода ключа может не
быть вовсе, и при `verifySignatures` клиент не войдёт — без внятной причины.
Для случая «мода нет нигде» это пишется в отчёт явно: **«у мода нет ключа,
сервер проверяет подписи»**.

### Путь к моду — не ограничение

Моды подключаются не по настоящему адресу: [_mods_arg](../core/launcher.py#L176)
раскладывает junction-ссылки в одну папку рядом с игрой и передаёт относительные
пути. Папка мода может лежать где угодно, хоть на другом диске. Механизм уже
есть.

## 6. Отчёт

Отдаётся **всегда, в том числе при провале** — там он нужнее всего.

```json
{"ok": true, "preset": "dev",
 "pack": {"mode": "normal",
          "built": [{"mod": "KR_Core", "source": "Core_Scripts", "seconds": 34,
                     "log": "C:\\temp\\Core_Scripts.packing.log"}],
          "skipped": 7, "failed": []},
 "server": {"requested": true, "ready": true, "pid": 9128, "port": 2302,
            "seconds": 47,
            "logs": {"rpt": "...", "script": "...", "adm": "..."}},
 "client": {"requested": true, "ready": true, "pid": 4412, "seconds": 14,
            "logs": {"rpt": "...", "script": "..."}},
 "problems": [{"side": "server", "kind": "script_error", "line": 812,
               "text": "Can't compile Server 'KRMedical' script module!"}]}
```

Обязательные свойства:

1. **Стороны раздельно.** «Сервер поднялся, клиент нет» — обычное дело, и это
   разные поля с разными состояниями.
2. **Прямые пути ко всем логам** — RPT, `script.log`, ADM, крэш-дампы, логи
   запаковки. Чтобы читать, а не искать.
3. **Ошибки скриптов и падения — в `problems`, и никогда не влияют на код
   возврата.** Наше дело сообщить факт; что с ним делать, решает вызывающий.
4. **По каждому моду своё время и свой лог.** Запаковка последовательная —
   pboProject под общим замком ([core/packer.py:27](../core/packer.py#L27)),
   одновременно работает ровно один. На трёхминутной сборке иначе непонятно,
   что тормозит.
5. **Версия протокола в каждом ответе** — обновление QTS не должно ломать чужой
   инструмент молча.

### Коды возврата

Отвечают только на вопрос «поднялось или нет».

| Код | Значение |
|---|---|
| 0 | всё запрошенное поднялось |
| 1 | не понял аргументы |
| 2 | нет пресета или программа не настроена |
| 3 | запаковка не удалась |
| 4 | сервер не поднялся за отведённое время |
| 5 | клиент не поднялся |
| 6 | упало уже после старта |
| 7 | не удалось связаться с QTS |

**`-wait` считается отдельно от запаковки.** Иначе `-wait=180` на большом
проекте истечёт на сборке, ещё до старта сервера, и мы получим «не поднялся»
там, где всё в порядке.

## 7. Что «гибко» значит на практике

Вызывать будут из чего угодно — Python, C#, PowerShell, задачи редактора.
Гибкость обеспечивается не размером набора команд, а шестью решениями:

1. Версия протокола в каждом ответе.
2. Команда `capabilities` (она же `-help -json`): инструмент спрашивает, что
   умеет **этот** QTS, а не гадает по номеру версии.
3. Параметры именованные, порядок не значим.
4. Новые параметры только необязательные; старые не удаляются.
5. Неизвестная команда — ошибка со списком, а не молчание.
6. Идентификатор запроса в ответе: можно слать несколько, не путаясь.

При таких правилах набор команд можно наращивать бесконечно, не ломая уже
написанные инструменты.

## 8. Справка

**Справку не пишем — собираем.** У каждого параметра в
[core/params.py](../core/params.py) уже есть описание на трёх языках
(`tooltip()` через `tr("param.<имя>")`), и оно же показывается в окне. Значит
справка не может устареть: её никто не пишет руками.

```
qtsctl -help              человеку: разделы, примеры, описания
qtsctl -help -json        программе: команды и параметры с типами
qtsctl -help mods         подключение, сорсы, привязка, забывание
qtsctl -help pack         типы запаковки, пересборка, логи
qtsctl -help params       полный список параметров клиента и сервера
qtsctl -help exit         коды возврата и формат отчёта
```

Первая страница — не описание грамматики, а **пять готовых команд**: справку
читают не чтобы изучить, а чтобы скопировать. Правило плюса и минуса — первым
абзацем, до любых списков.

Четыре обязательных свойства:

1. **`-help` работает всегда** — когда программа не настроена, когда QTS не
   запущен, когда пресета нет. Справка живёт в самом `qtsctl` и в канал не
   лезет.
2. **Неизвестный аргумент ведёт к справке, а не в тупик:** «Не знаю
   `+cFilePathing`. Похоже на `+cFilePatching`. Полный список: `-help params`».
   Опечатка обязана быть громкой — молчаливое игнорирование даст «тест прошёл»
   там, где проверялось не то.
3. **Язык — как в приложении**, через те же словари. Имена аргументов не
   переводятся никогда: `+cFilePatching` — параметр DayZ.
4. **Без раскраски и рамок:** вывод часто едет в панель редактора или в файл.

И то же самое — в приложении: страница «Внешнее управление» с состоянием, путём
к `qtsctl`, теми же примерами и кнопкой «скопировать». Возможность, о которой
знает только тот, кто догадался запустить с `-help`, нарушает наше же правило о
скрытом знании.

## 9. Как это устроено внутри

### Транспорт

Канал уже есть — [ui/single_instance.py](../ui/single_instance.py). Сейчас по
нему ходят две строки (`show`, `launch:<пресет>`); нужен словарь побогаче:
строка JSON в запрос, строка в ответ.

На Windows `QLocalServer` — это именованный канал `\\.\pipe\KR_QTS_<юзер>`, и
открывается он **обычным `open()`**. Клиенту не нужен ни Qt, ни PySide: в C# это
`NamedPipeClientStream`, в PowerShell то же самое, в Python — стандартная
библиотека. Права уже правильные: канал персональный, чужой пользователь не
достучится, токены не нужны.

HTTP на localhost отброшен: занятый порт, брандмауэр, токен, доступность с
других машин — ради локального инструмента это лишнее.

### Консольный вход

Оконная сборка в stdout писать не умеет и не должна: консоль прячется первой
строкой `main()`, иначе помощники pboProject плодят окна. Значит нужен отдельный
маленький `qtsctl.exe`, который внутри стучится в тот же канал. Для задачи в
редакторе это не «когда-нибудь потом», а условие работы.

### Headless

`core/` уже свободен от интерфейса — виджетов там нет (единственное исключение,
[core/crashguard.py](../core/crashguard.py), намеренное). А оркестровка живёт в
окне: [ui/main_window.py](../ui/main_window.py) — 2281 строка, и в ней не только
кнопки, но и состояние запуска, подхват процессов, сторож, RCon, мониторы
памяти, реакция на падения. Плюс 23 места, где программа задаёт вопрос диалогом.

Форма: не «вторая версия», а **один процесс на пользователя, у которого окно
необязательно**.

```
KR_QTS.exe             движок и окно — человеку
KR_QTS.exe --headless  только движок — инструменту, сборочной машине
```

Одна копия на том же канале. Инструмент стучится; никого нет — поднимает
headless, и на машине не появляется ни окна, ни значка в трее. Человек в это
время работает с окном — инструмент попадает **в ту же копию**, а не заводит
вторую. Двух владельцев одного сервера не бывает никогда.

**Headless не спрашивает.** Спрашивать снаружи некого, а процесс, замерший в
ожидании ответа, — худший вид поломки для скрипта. Отсюда:

* проверки перед запуском получают режим «только отчёт»
  ([core/preflight.py](../core/preflight.py) отчёт уже строит, решение принимает
  окно);
* на ненастроенной машине честный ответ «нужен мастер», а не догадки;
* все 23 диалога превращаются в коды ошибок. Для окна ничего не меняется — оно
  так же покажет диалог, просто по коду от движка.

**Жизнь процесса:** живёт, пока есть что сторожить, плюс время простоя после
последней команды, плюс явный `quit`. Иначе на машине копятся забытые процессы.

## 10. Порядок работ

Два этапа, чтобы рабочий интерфейс появился раньше тяжёлого рефактора.
**Протокол между этапами не меняется** — написанное на первом продолжает
работать.

### Этап 1. Интерфейс поверх нынешнего окна

1. Протокол: JSON-строки в существующем канале, версия, идентификатор запроса,
   ошибки со списком.
2. Разбор грамматики: правило `+`/`-`, генерация форм из
   [core/params.py](../core/params.py), моды и сорсы, запаковка.
3. Отчёт и коды возврата; пути к логам; `problems` из
   [scriptmem](../core/scriptmem.py) и [crashlog](../core/crashlog.py).
4. `qtsctl.exe` — консольный вход, вывод в stdout.
5. Справка, собранная из справочника, плюс `-help -json`.
6. Регистрация модов и сорсов, `-forget`.
7. Страница «Внешнее управление» в настройках.
8. Прогон в [tests/smoke.py](../tests/smoke.py): грамматика разбирается, справка
   строится, коды возврата на месте.

На этом этапе QTS поднимается свёрнутым в трей, как по ярлыку.

### Этап 2. Движок отдельно от окна

9. Оркестровка уезжает из [ui/main_window.py](../ui/main_window.py) в
   `core/engine.py`; окно становится представлением.
10. Диалоги превращаются в коды ошибок.
11. `--headless`, жизненный цикл процесса, режим «только отчёт» у проверок.
12. Показ окна поверх работающего движка по команде `show`.

Этап 2 — самый крупный рефактор в проекте, но он же чинит то, что окно сейчас
знает слишком много.

### Совместимость

Нынешний `--launch <пресет>` остаётся рабочим: ярлыки быстрого запуска не должны
сломаться. Он становится синонимом `-preset <имя> +server +client`.

## 11. Открытые вопросы

1. **`client.ready` — «процесс жив» или «игрок подключился»?** Сейчас клиент
   считается поднявшимся, если процесс прожил N секунд и не упал; он при этом
   может стоять в главном меню или не найти сервер. Честный признак у нас один —
   спросить сервер по RCon, появился ли игрок. Полезнее для автотеста, но
   требует настроенного RCon в пресете.
2. **Моды только для клиента.** Сейчас понятия нет: в
   [ModInfo](../core/mods.py#L171) только `is_server`. Если нужен — это новая
   возможность, и добавлять её придётся и в окно тоже, иначе командная строка
   станет умнее приложения.
3. **`-wait` по умолчанию.** Предлагается: включён для консольного входа
   (скрипт почти всегда хочет знать, поднялось ли), выключен для ярлыка;
   `+detach` возвращает управление сразу.
4. **«Собрать только вот этот мод, остальное не трогать»** — уточнение к
   `+pack`, нужно на больших проектах с долгой сборкой.
5. **Показ окна поверх headless-процесса** (`show`) — нужен или достаточно
   жёсткого разделения режимов.
6. **Другая машина.** Если инструменты когда-нибудь поедут на отдельную
   сборочную или тестовую машину, именованного канала не хватит и выбор
   транспорта придётся пересматривать. Пока считаем, что всё локально.
